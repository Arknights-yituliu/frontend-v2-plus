# RIIC 排班生成器开发协作规则与边界

本文用于向参与 RIIC（基建）排班生成器开发的协作者说明：

- 写代码、改数据和做研究时分别遵守什么规则；
- 前端代码与上游规则/数据维护方各自拥有什么权限；
- 什么内容可以进入前端运行时；
- 什么时候可以同步数据、修改契约或发布版本。

本文是外发版交接用汇总，不包含内部工作区路径、原始排班、私有研究资料或未发布数据。发生冲突时，以项目仓库中的正式规范和当前发布说明为准。

## 一、参与方与所有权

### 1. 前端 Scheduler

负责：

- 前端排班生成器和运行时 consumer 代码；
- 前端 consumer contract；
- 上游规则/数据版本的接入、验收和同步；
- 已批准 runtime package 的消费和展示验证；
- 前端自身的候选匹配、排班计算、收益结算和 UI 行为。

### 2. 协作者的基本原则

- 不跨越目录所有权直接修改另一方的数据或规则；
- 不把未验收的 preview、debug package 或临时数据自动当成正式发布输入；
- 不因为“看起来应该这样”而擅自确定产品规则、数据口径或公开范围；
- 修改前先确认目标文件、数据所有者、发布状态和同步授权。

## 二、协作与提问规则

- 只有当需求存在会影响功能、范围、数据或用户体验的关键歧义时，才先向用户提问。
- 可以通过阅读代码、配置、现有数据和文档确定的内容，先自行调查，不反复询问。
- 小型、明确、低风险的修改可以直接完成。
- 不确定业务规则、产品预期、数据归属或发布授权时，不替用户做决定。
- 每次提问集中处理真正影响决策的问题，避免把可调查的问题转给用户。
- 修改完成后说明：已经自动验证的内容、建议人工验证的内容，以及仍未验证的风险。

## 三、验证规则

验证目标是尽快得到足够可信的结果，不机械执行所有测试。

### 低风险修改

对于只涉及文案、颜色、间距、布局或简单交互的修改：

- 默认由用户人工确认；
- 不因为“改了前端”就自动启动开发服务器、浏览器、Playwright、截图或视觉回归测试；
- 完成后提供访问路径、操作步骤和预期结果。

### 需要自动验证的修改

涉及以下内容时，应做有针对性的自动检查：

- 共享逻辑、数据处理、权限、存储或 API 契约；
- 复杂状态、排班生成、候选匹配、收益结算；
- 可能影响多个模块的公共行为；
- 难以通过人工观察确认的正确性问题。

### 视觉验证

计划启动开发服务器、浏览器、截图或 Playwright 前，应先说明原因、预计耗时和用户可采用的人工验证方式，并等待用户同意；除非更高优先级的任务明确要求视觉验证。

## 四、代码与仓库规范

### 常用命令

```bash
npm run dev
npm run build
npm run preview
npm run server
```

项目是 Vue 3 + Vite 多入口前端，构建包含 `index.html` 和 `docs.html`。

### 编码约定

- 使用项目既有的 Vue Composition API、组件库和工具函数；
- Vue 组件使用 PascalCase；路由页面遵循现有目录结构；
- 导入路径保持文件内现有风格，优先使用项目既有绝对路径或 `@` 别名；
- 遵循 Prettier 约定：2 空格缩进、分号、双引号、ES5 尾逗号、print width 160；
- 保持 diff 聚焦，不顺手做无关重构、格式化或元数据修改；
- 不提交密钥、token 或其他敏感配置；
- 修改大型 JSON 前先验证格式和结构；
- 不增加临时 HTML 入口，不绕开现有 Vite 多入口配置；
- 新增功能优先补充针对性测试；当前项目没有固定测试运行器，测试可优先采用 Vitest + Vue Test Utils。

### 提交与协作

提交信息格式：

```text
提交类型(提交涉及的模块): 提交内容
```

常用类型包括 `feat`、`fix`、`update`、`css`、`style`、`optimized`、`refactor`、`perf`、`test`、`docs`、`chore` 等。

提交或 Pull Request 前应：

1. 使用 `git status` 确认改动范围；
2. 保证无关文件没有被带入；
3. 按风险运行必要的检查；
4. 在 PR 中说明行为变化、验证结果和已知限制。

## 五、排班生成器 V1 / V2 分工

### V1 当前范围

V1 继续维护：

- 当前候选目录和 fallback；
- 房间组排班；
- 自动选房与补位；
- 控制中枢选择和校准；
- 第三层规则的已批准消费；
- 排班预览、MAA 导出和收益结算。

### V2 方案状态

V2 方案是研究结论，不是 V1 修改授权。未经重新立项确认，不得据此修改 V1 前端、运行时发布包或既有 JSON。

V2 计划中的通用设计边界：

- 将跨站套组、站内组合、单干员候选和补位后的完整房间视为完整方案单元；
- 跨站套组必须在干员、房间位置、中枢预约位和规则条件全部满足时才成立；
- 使用完整试排后的增量收益比较方案，而不是简单相加成员标称效率；
- 跨站收益只能计算一次，必须扣除被挤掉的候选、补位和中枢收益；
- 两班方案必须按班次分别验证，不能把一个套组拆成两班的一半；
- V2 目标是近优排班，不承诺全局最优；
- 前端不得按干员姓名新增业务特判，上游规则/数据维护方也不预先维护“套组 A 永远优于套组 B”的冲突表。

### 事实与计算的边界

上游规则/数据维护方维护可读事实，例如：

- 持有干员和精英等级条件；
- 布局、房间数量和触发条件；
- 人员去向、房间预留和中枢预约；
- 额外贡献、排序修正和两班完整性要求。

前端维护通用计算，例如：

- 条件匹配；
- 规则展开为方案单元；
- 冲突识别；
- 试排、收益计算和排序；
- 最终班表生成。

## 八、修改前检查清单

- [ ] 已确认需求没有关键歧义，或已经提出必要问题；
- [ ] 已确定要修改的是前端代码、前端公开 runtime data，还是上游 source/release；
- [ ] 已确认文件所有者和当前发布状态；
- [ ] 已确认不会把私有数据、原始排班或未发布候选带入前端；
- [ ] 已确认这不是仅凭 V2 研究方案修改 V1；
- [ ] 已选择与风险匹配的验证方式；
- [ ] 已检查当前工作区中是否存在他人的未提交改动。

## 九、提交或同步前检查清单

- [ ] 改动范围和数据来源已经记录；
- [ ] 自动验证已经执行，或明确说明未执行原因；
- [ ] 手工验证步骤和预期结果已经写明；
- [ ] 已知风险和未验证内容已经写明；
- [ ] 如涉及上游 package，已记录 release ID、manifest/hash 和 validation 结果；
- [ ] 如涉及前端同步，已取得明确同步批准；
- [ ] 没有修改上游数据来解决前端 consumer 问题；
- [ ] 没有把 debug package 当作正式发布包；
- [ ] PR 或提交信息符合仓库约定。
