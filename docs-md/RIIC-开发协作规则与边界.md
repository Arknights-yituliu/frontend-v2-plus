# RIIC 排班生成器开发协作规则与边界

本文用于向参与 RIIC（基建）排班生成器开发的协作者说明：

- 修改代码和运行时数据时应遵守什么规则；
- 页面、计算逻辑和数据文件之间的边界；
- 什么内容可以进入公开运行时；
- 如何验证并提交代码和数据变更。

本文是外发版协作说明，不包含内部工作区路径、个人排班资料或非公开研究材料。项目代码和运行时数据统一在本项目内维护，通过常规代码评审和版本管理协作。发生冲突时，以项目仓库中的正式规范和当前发布说明为准。

## 一、协作范围与变更归属

排班生成器的页面、计算逻辑、候选数据和规则数据均在本项目内维护，并通过同一套代码评审和版本管理流程协作。

协作者应：

- 修改前确认变更涉及的源码、运行时数据和消费逻辑；
- 不把本地临时文件、调试输出或未经核对的外部资料直接当成正式运行时数据；
- 不因为“看起来应该这样”而擅自确定产品规则、数据口径或公开范围；
- 规则或候选数据发生变化时，同时检查对应消费者、数据结构和展示结果；
- 通过项目现有的代码评审和版本管理流程提交变更。

## 二、协作与提问规则

- 只有当需求存在会影响功能、范围、数据或用户体验的关键歧义时，才先向用户提问。
- 可以通过阅读代码、配置、现有数据和文档确定的内容，先自行调查，不反复询问。
- 小型、明确、低风险的修改可以直接完成。
- 不确定业务规则、产品预期、数据口径或公开范围时，不替用户做决定。
- 每次提问集中处理真正影响决策的问题，避免把可调查的问题转给用户。
- 修改完成后说明：已经自动验证的内容、建议人工验证的内容，以及仍未验证的风险。

## 三、验证规则

验证目标是尽快得到足够可信的结果，不机械执行所有测试。

### 低风险修改

对于只涉及文案、颜色、间距、布局或简单交互的修改：

- 默认由用户人工确认；
- 不因为“改了前端”就自动启动开发服务器、浏览器、Playwright、截图或视觉回归测试；
- 完成后提供访问路径、操作步骤和预期结果。

### 需要自动验证的修改

涉及以下内容时，应做有针对性的自动检查：

- 共享逻辑、数据处理、权限、存储或 API 契约；
- 复杂状态、排班生成、候选匹配、收益结算；
- 可能影响多个模块的公共行为；
- 难以通过人工观察确认的正确性问题。

### 视觉验证

计划启动开发服务器、浏览器、截图或 Playwright 前，应先说明原因、预计耗时和用户可采用的人工验证方式，并等待用户同意；除非更高优先级的任务明确要求视觉验证。

## 四、代码与仓库规范

### 常用命令

```bash
npm run dev
npm run build
npm run preview
npm run server
```

项目是 Vue 3 + Vite 多入口前端，构建包含 `index.html` 和 `docs.html`。

### 编码约定

- 使用项目既有的 Vue Composition API、组件库和工具函数；
- Vue 组件使用 PascalCase；路由页面遵循现有目录结构；
- 导入路径保持文件内现有风格，优先使用项目既有绝对路径或 `@` 别名；
- 遵循 Prettier 约定：2 空格缩进、分号、双引号、ES5 尾逗号、print width 160；
- 保持 diff 聚焦，不顺手做无关重构、格式化或元数据修改；
- 不提交密钥、token 或其他敏感配置；
- 修改大型 JSON 前先验证格式和结构；
- 不增加临时 HTML 入口，不绕开现有 Vite 多入口配置；
- 新增功能优先补充针对性测试；当前项目没有固定测试运行器，测试可优先采用 Vitest + Vue Test Utils。

### 提交与协作

提交信息格式：

```text
提交类型(提交涉及的模块): 提交内容
```

常用类型包括 `feat`、`fix`、`update`、`css`、`style`、`optimized`、`refactor`、`perf`、`test`、`docs`、`chore` 等。

提交或 Pull Request 前应：

1. 使用 `git status` 确认改动范围；
2. 保证无关文件没有被带入；
3. 按风险运行必要的检查；
4. 在 PR 中说明行为变化、验证结果和已知限制。

## 五、RIIC 运行时数据边界

运行时规则和候选数据与消费它们的代码在同一项目中维护。提交数据变更时应：

- 使用项目实际消费的数据结构，不额外引入没有消费者的私有字段或调试产物；
- 保留必要的来源、条件和计算口径，使规则可以被核查；
- 检查 JSON 格式、字段类型、引用标识和对应消费者的兼容性；
- 将数据 diff 与相关代码变更一并评审，不通过手工覆盖或绕开版本管理更新运行时文件；
- 不提交个人凭证、个人排班导出、非公开研究笔记或其他不应公开的材料。

发现数据或消费者问题时，在本项目对应的规则、数据或计算模块中修正，并提供可复核的变更说明；不要用临时调试文件替换正式运行时数据。

## 六、排班生成器 V1 / V2 范围

### V1 当前范围

V1 继续维护：

- 当前候选目录和 fallback；
- 房间组排班；
- 自动选房与补位；
- 控制中枢选择和校准；
- 第三层规则和候选数据的运行时消费；
- 排班预览、MAA 导出和收益结算。

### V2 方案状态

V2 方案描述的是后续架构方向，不自动构成修改 V1 行为的授权。若要把 V2 方案落入现有 V1 流程，应先明确目标范围、兼容要求和验收方式。

V2 计划中的通用设计边界：

- 将跨站套组、站内组合、单干员候选和补位后的完整房间视为完整方案单元；
- 跨站套组必须在干员、房间位置、中枢预约位和规则条件全部满足时才成立；
- 使用完整试排后的增量收益比较方案，而不是简单相加成员标称效率；
- 跨站收益只能计算一次，必须扣除被挤掉的候选、补位和中枢收益；
- 两班方案必须按班次分别验证，不能把一个套组拆成两班的一半；
- V2 目标是近优排班，不承诺全局最优；
- 不按干员姓名在通用计算代码中新增业务特判，也不预先维护“套组 A 永远优于套组 B”的固定冲突表。

### 事实与计算的边界

运行时规则和候选数据声明可核查的事实，例如：

- 持有干员和精英等级条件；
- 布局、房间数量和触发条件；
- 人员去向、房间预留和中枢预约；
- 额外贡献、排序修正和两班完整性要求。

排班计算代码负责通用计算，例如：

- 条件匹配；
- 规则展开为方案单元；
- 冲突识别；
- 试排、收益计算和排序；
- 最终班表生成。

## 七、修改前检查清单

- [ ] 已确认需求没有关键歧义，或已经提出必要问题；
- [ ] 已确认要修改的代码、规则或候选数据文件及其消费者；
- [ ] 已确认数据字段和引用符合当前运行时结构；
- [ ] 已确认不会把个人资料、非公开材料或临时调试数据带入运行时；
- [ ] 已确认这不是仅凭 V2 研究方案修改 V1；
- [ ] 已选择与风险匹配的验证方式；
- [ ] 已检查当前工作区中是否存在他人的未提交改动。

## 八、提交前检查清单

- [ ] 改动范围和数据来源已经记录；
- [ ] 自动验证已经执行，或明确说明未执行原因；
- [ ] 手工验证步骤和预期结果已经写明；
- [ ] 已知风险和未验证内容已经写明；
- [ ] 如涉及运行时数据，已记录来源、字段变化及对应消费者；
- [ ] 数据结构和引用已通过针对性检查；
- [ ] 没有用调试产物或本地临时文件替换正式运行时数据；
- [ ] PR 或提交信息符合仓库约定。
